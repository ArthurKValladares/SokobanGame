Engine review · Sokoban 3D · 64,900 LOC C++20 / Vulkan 1.3

What stands between this and a modern 3D engine

The gameplay, tooling, packaging and test discipline here are well above the usual bar. The renderer is not a small 3D engine — it is a very refined fixed-camera tile-board rasterizer, and almost every gap below descends from that one fact.

Findings carry stable IDs (T3, V1, …). §9 sequences them into phases, so each step there is a task you can hand to someone. Nine findings were corrected after implementation revealed the original reasoning was wrong; each says so where it stands.

Implementation status is marked on each finding — look for the Done, Partly done and Next up chips and the note under each heading, and for the same marks on every step of the plan in §9. Everything below a status note describes the code as it stood at review time, in the present tense, and has deliberately not been rewritten — the finding is the record of what was found. The note above it is what is true now. §11 records what building this document’s recommendations proved wrong about them. The working notes that go with it live in HANDOFF.md at the repo root; that file, not this one, is where the invariants each landed step established are written down.

01

The governing constraint: the renderer has no camera

Before any individual finding, one architectural fact explains most of the list. There is no view or projection matrix anywhere on the GPU. The CPU projects every vertex to clip space and ships the four corners of each quad in push constants. The plan in §9 refers to fixing this as C1 — it is the only work item that is a whole section rather than a single finding.

// shaders/triangle.vert.glsl — the entire vertex transform
const int index = indices[gl_VertexIndex];
gl_Position       = pc.vertices[index];
outShadowPosition = pc.shadowVertices[index];
outWorldPosition  = worldFromSunShadow(outShadowPosition);

Three consequences follow directly, and they are the root of sections 2 and 3:

  • World position is recovered by inverting the sun's shadow projection (worldFromSunShadow, duplicated verbatim in four shaders). The shadow frustum is the only spatial frame the GPU has. Any effect needing a real world or view position — fog, parallax, screen-space reflections, correct specular, distance-based anything — has no supply.
  • The view direction is a hardcoded constant. triangle.frag.glsl:301 declares const vec3 viewDirection = normalize(vec3(0.0, 0.25881904, 0.9659258)); — the fixed isometric camera baked into the shader. Specular highlights are correct only for that one camera. Move the camera and the lighting is wrong everywhere.
  • Geometry is push-constant sized. TilePushConstants is static_assert(sizeof(...) == 256) — exactly the Vulkan guaranteed minimum, with zero bytes free. Your own handoff notes this twice ("the 256-byte push-constant block is completely full"). Every new per-draw parameter now requires evicting an existing one, and the ground-splat pass already reuses slots the ground path "leaves free."
Read this way

This is not a bad renderer. For an isometric board of a few hundred tiles it is a legitimate, even clever design — the CPU has the geometry anyway for picking, so pushing clip-space corners skips vertex buffers entirely. It is simply a design whose ceiling is the board. Everything below is the cost of raising that ceiling.

02

Foundations that don't exist yet

These are not features. They are the substrate every 3D feature is written against, and none of them can be retrofitted cheaply once more code depends on their absence.

F1FoundationDone

There is no math library

Done. Done in Phase 1.

src/engine/Math.hpp · src/engine/render/GltfMesh.hpp:39 · IsoScenePreparer.cpp:25 · GltfMesh.cpp:728 · DecorationGizmo.cpp:19 · EditorInteraction.cpp:15

Math.hpp contains Vec2/Vec3/Vec4/GridPosition as plain structs with no operators. There is no matrix type, no quaternion, no transform, no AABB, no ray, no frustum, no plane. Mat4 is std::array<float,16> declared inside the glTF mesh loader header — so anything wanting a matrix must include the asset loader. add(), dot(), normalize() are independently re-implemented in at least four anonymous namespaces.

This is why the renderer works in pre-projected corners: composing a model→world→view→clip chain is currently a manual, error-prone thing nobody wants to write twice. It is also why model.vert.glsl rotates normals with three sin/cos pairs per vertex from Euler angles instead of a normal matrix.

DoA real Math module: Mat3/Mat4 with multiply/inverse/transpose/TRS-decompose, Quat with slerp, Transform, Aabb, Sphere, Plane, Frustum, Ray, operator overloads, and unit tests. Everything in sections 3–6 is either easy or impossible depending on whether this exists. This is the single highest-leverage change in the review.
F2FoundationPartly done

The whole pipeline is 8-bit LDR sRGB — no HDR, no tonemapping, no exposure

Partly done. F2a and F2b are done: an R16G16B16A16_SFLOAT scene target and a tonemap pass, with the "AO modulates ambient" half of V7 pulled forward into it. F2c — a real curve and a user-facing exposure control — is deliberately still open.

VulkanSwapchainResources.cpp:906, 716–825 (all attachments use colorFormat_) · zero matches for tonemap/exposure/ACES/HDR across src/ and shaders/

Every render target — MSAA color, resolved color, sampled scene color — is created with the swapchain format, which chooseSurfaceFormat picks as VK_FORMAT_B8G8R8A8_SRGB. Lighting is computed in linear space and hardware-encoded on write, so gamma is correct; the problem is range. There is no headroom above 1.0, so bright surfaces clip hard, and there is no exposure control, no tonemap curve, and no place to put one.

This blocks, by construction: bloom, emissive materials, physically-meaningful light intensities, any HDR display output, and any post-process chain worth having. The sun intensity slider maxes at 4.0 and simply saturates.

DoRender the scene into R16G16B16A16_SFLOAT (or B10G11R11 if bandwidth matters), add a tonemap+encode fullscreen pass as the last step before the swapchain blit, and move the sRGB encode there. The upscale path in upscaleSceneToSwapchain is the natural place to grow it.
F3FoundationDone

No material model — one baseColor texture and a scroll flag

Done. Done in Phase 2, as F3a (tangents, a second UV set, a wider vertex), F3b (the material model on the CPU, then a GPU material buffer at descriptor binding 12), and F3c (Cook-Torrance GGX). The map slots this finding also asks for — normal, metallic-roughness, emissive, occlusion — are uploaded but unread: the manifest cannot name them yet, which is the work scheduled straight after V4.

GltfMesh.hpp:14–31 (MeshVertex) · triangle.frag.glsl:197–351 · AssetManifest material modes

The vertex format is position, normal, uv, textureIndex, materialFlags. No tangents, no vertex colors, no second UV set. Materials come entirely from the manifest — none, texture, or primitive-materials — and the only per-material behavior is scrollV. The glTF loader never reads pbrMetallicRoughness, normalTexture, emissiveTexture, occlusionTexture, alphaMode, or doubleSided at all.

Lighting is ad-hoc Blinn-Phong with a wrapped-diffuse blend and a skyFill hack for ambient:

float diffuse = mix(lambertDiffuse, wrappedDiffuse * wrappedDiffuse, 0.65);
float skyFill = smoothstep(-0.35, 1.0, normal.z);
diffuseLighting = ambient * (1.0 + skyFill * 0.35) + sunRadiance * diffuse * shadow + …;

Without tangents there is no normal mapping. Without metallic/roughness there is no PBR. Without an alpha mode there is no cutout foliage. Every modern asset you buy or author assumes all three.

DoExtend MeshVertex with tangent + optional second UV; parse glTF materials into a real Material struct (baseColor factor+texture, metallic-roughness, normal, emissive, occlusion, alpha mode/cutoff, double-sided); move to a Cook-Torrance GGX BRDF. Do this after HDR exists, since PBR values without range headroom look worse than what you have.
F4Foundation

One über-shader does scene, models, UI text, title art, editor highlights and blur

Not started. Now the largest remaining Foundation item, and F3 has made the branch count worse exactly as this document predicted — triangle.frag.glsl is 576 lines and carries a full Cook-Torrance implementation beside the UI font and the title art. Sequenced after V4 and the glTF map work, not before.

shaders/triangle.frag.glsl — 382 lines, 7 material modes selected by textureOptions.x

Modes 1–7 branch between tile color, model textures, the UI font atlas, the title background, a procedural particle texture, and a scene-image composite with a rounded-rect SDF. Editor highlight tinting, Bayer dither for previews, and a 5×5 gaussian read-back of the scene are all in the same fragment shader as the lighting. There are no specialization constants and no shader permutation system — 14 fixed SPIR-V modules feeding 16 fixed pipelines.

DoSplit UI out of the scene shader entirely; introduce specialization constants or a small permutation key (shadows on/off, AO on/off, skinned, material features) so the scene shader stops paying for branches it isn't using and so new features don't have to fit in the same file.
F5Debt

No RHI seam — zero virtual functions in the entire engine

Application.hpp:26,140 (VulkanRenderer renderer_; by value) · grep -rn "virtual " src/engine → 0

Application owns a concrete VulkanRenderer. Every render type — VkDescriptorSet, VkRect2D, ImageData — reaches the shell layer directly. Practically this means Windows/Vulkan is the only target that will ever build, and there is no seam for a headless/null backend to test rendering logic against.

DoYou do not need a full RHI. But do introduce a narrow IRenderer (or a compile-time backend typedef) at the Application boundary and stop leaking Vk* types into Ui/DebugUi signatures. That alone buys you a null backend for CI, which section 8 needs.
03

Throughput: the frame is bound by construction

Several independent decisions each cost throughput, and they compound. Individually defensible for a board; collectively they cap the scene at roughly its current size.

T1ThroughputDone

One draw call per quad, with 256 bytes of push constants each

Done. Done in Phase 1. Cost roughly ten times what this document estimated; see §11.

VulkanSceneRecorder.cpp — vkCmdDraw(cb, 6, 1, 0, 0) at ~10 sites: drawFace, drawGroundSplatFace, drawWaterFace, drawMirrorEnergyFace, drawParticle, grid overlay

Every tile face, every water surface, every particle, and every grid line is vkCmdSetPrimitiveTopology + vkCmdPushConstants(256) + vkCmdDraw(6). A 20×20 board with height is on the order of a thousand quads before particles, and the grid overlay adds one draw per line in each axis. Models are batched properly (see OpaqueDrawSorter) — the tile geometry, which is the bulk of the scene, is not batched at all.

DoOnce a real transform pipeline exists (§2), tiles become instanced geometry: one unit-cube mesh, a per-instance SSBO of transforms and material indices, one vkCmdDrawIndexed with instanceCount = N. This is the same mechanism model.vert.glsl already uses via modelInstances — it just needs to reach tiles.
T2ThroughputDone

Opaque geometry is alpha-blended and sorted back-to-front

Done. Done in Phase 0.

VulkanPipelineFactory.cpp:332 .blendEnable = VK_TRUE on all nine scene pipelines · IsoScenePreparer.cpp:1138–1142 std::ranges::sort(scene.opaqueFaceIndices, fartherFirst)

Every scene pipeline — scene_, model_, skinnedModel_, groundSplat_, ui_ — is created with SRC_ALPHA / ONE_MINUS_SRC_ALPHA blending enabled, and opaque faces are then sorted farthest first. Back-to-front is the painter's-algorithm order: it guarantees every hidden surface is shaded and then overwritten.

CorrectionAn earlier draft of this review said the blending was what stopped early-Z. That was wrong, and it is worth being precise because it changes the expected payoff. Blending happens after the fragment shader and does not disable early depth testing; what defers depth writes here is the discard in applyEditorPreviewDither, which every scene fragment pays for. So the two halves of this finding buy different things: dropping the blend unit on opaque draws saves colour-attachment read-modify-write bandwidth on every covered sample, which matters most at high MSAA, and the front-to-back sort lets the depth test reject occluded fragments. Both are real; neither is a step change on its own.

DoGive opaque draws a pipeline with blendEnable = VK_FALSE, sort them front-to-back, and keep the blended pipeline for the genuinely translucent list (water, mirror energy, ice blur, particles) already separated in translucentFaceIndices. Watch for faces that sit in the opaque list but carry a sub-1.0 alpha — the editor's ladder-rung preview does — and route those per face rather than per pass.
T3ThroughputDone

GPU backface culling is disabled everywhere

Done. Done in Phase 0.

VulkanPipelineFactory.cpp:317 .cullMode = VK_CULL_MODE_NONE · VulkanSceneRecorder.cpp:720, 863 vkCmdSetCullMode(cb, VK_CULL_MODE_NONE) · recordScenePass viewport .height = -extent.height

The pipeline default is NONE and the recorder explicitly sets NONE at record time. CPU-side faceVisible() does per-quad backface rejection for tiles, but every glTF mesh — the Rogue, the blocks, the conveyors, all decorations — rasterizes both sides of every closed surface.

The winding trapTurning culling on is not just a cull-mode change, and an earlier draft of this review got the reasoning wrong. It argued that mirror ghosts already culled BACK successfully and that this proved the assets wind consistently. It proved no such thing: a ghost is a translucent rim-lit effect, so drawing its interior looks acceptable, and that is exactly what had been happening. The scene pass uses a negative-height viewport to put +Y up in Vulkan's Y-down NDC, and a negative viewport height reverses the winding the rasterizer sees. glTF authors front faces counter-clockwise and nothing else in the chain flips them — the camera basis is right-handed, the projection applies no sign flip, decoration scale is clamped positive — so meshes arrive clockwise. Culling BACK against a COUNTER_CLOCKWISE front face therefore removes the outside of every model and leaves the inside: hollow.

DoSet VK_CULL_MODE_BACK_BIT for model draws together with VK_FRONT_FACE_CLOCKWISE, and keep NONE for tile quads, whose winding after CPU projection is not guaranteed. Restore both states after the model loop. Leave the shadow pass alone — it sets NONE explicitly and may rely on double-sided rendering to close depth. Expose a toggle: a model wound the other way disappears rather than degrading.
T4Throughput

No frustum culling, no occlusion culling, no LOD — anywhere

Zero matches for frustum/cull/occlusion in src/engine outside VK_CULL_MODE · IsoScenePreparer.cpp:504 faceVisible is backface-only

The only visibility test in the engine is the per-quad backface dot product. Everything authored in the level is projected, sorted and submitted every frame. There is no spatial index of any kind — no BVH, no octree, no grid of renderables. RenderFrameData caps at 16,384 tiles and 65,536 iso faces; there is no mechanism to stay under that other than authoring small screens.

DoThis needs §2's Frustum and Aabb first. Then: per-renderable bounds, a frustum test in IsoScenePreparer::prepare, and a coarse spatial structure once the world outgrows a screen. Occlusion culling and LOD chains are later, but the bounds you add now are what both will use.
T5Throughput

Point shadows re-render six cube faces per light, every frame, with no culling

VulkanSceneRecorder.cpp:399–452 · LightingConfig.hpp:44 pointShadowMapSize = 512 · RenderTypes.hpp:196 pointLightCapacity = 8

For each shadow-casting point light, all six faces are re-recorded and every entry of scene.shadowFaces is drawn individually into each — up to 48 additional render passes per frame, each with a full pass over the scene's shadow geometry, each face draw being its own vkCmdDraw(6). There is no range test against the light's sphere, no static/dynamic caching, no face skipping when nothing in that direction changed, no shadow distance fade.

The directional shadow is the opposite extreme: one 2048² map covering the whole board with no cascades, which is fine for a board and will not survive a larger world.

DoCull casters against each light's range before recording; cache static-geometry cube faces and only re-render faces containing moved geometry; consider a shared shadow atlas with per-light tile sizing by screen-space importance. Add CSM to the sun only when the view distance actually grows.
T6ThroughputDone

MSAA 8× at full internal resolution is the shipping default

Done. Done in Phase 0.

UserSettingsConfig.hpp:18 antiAliasingSamples = 8 · RendererReconfiguration.hpp:15 Msaa8x

MSAA 8× is the default and the only anti-aliasing available — there is no FXAA, no SMAA, no TAA, and no upscaler (FSR/XeSS/DLSS). Stacked on top of blend-enabled opaque geometry with no early-Z and no backface culling, 8× samples multiply the fragment work you are already not rejecting. It is also the AA technique least compatible with the deferred/compute-based direction a modern renderer takes.

DoDrop the default to 4× now (measure it — with §3's other fixes 8× may become affordable again). Longer term, TAA plus a spatial upscaler replaces MSAA entirely and gives you temporal accumulation for AO, shadows and reflections as a bonus.
T7ThroughputDone

A full-resolution depth copy every frame, for an AO pass that may be off

Done. Done in Phase 0.

VulkanSwapchainResources.cpp:383–484 copyResolvedSceneDepth · VulkanSceneRecorder.cpp:485, 544 (both call sites unconditional) · VulkanSsaoPass.cpp:78 (the pass itself early-returns)

CorrectionAn earlier draft of this review named the scene-colour copy here. That was wrong: copyResolvedSceneColor is already gated behind hasTranslucentContent, the level-transition amount, and the preview being active. The unconditional one is the depth copy.

copyResolvedSceneDepth runs after every opaque pass — a full render-extent vkCmdCopyImage plus four barriers. Its only consumer is the SSAO occlusion pass, which reads descriptor binding 5 and early-returns when ambient occlusion is disabled or its strength is zero. With AO off, the frame pays for the copy and nothing reads it.

DoGate the copy on the same predicate the pass uses, and put that predicate in one place both call. While you are here, the blur-behind path is still a 25-tap loop inside the main fragment shader; a half-res separable two-pass gaussian would be cheaper and better.
T8Throughput

The whole frame is single-threaded: one queue, one command pool, one thread

VulkanDeviceContext.cpp:340–403 (one graphics queue) · :406 (one command pool) · Application.cpp:349–566 (linear loop) · handoff: "deliberately no worker command pools, dedicated transfer queues, or concurrent Vulkan uploads"

Input → simulation → UI → scene preparation (full CPU projection and sort of every face) → command recording → submit → pace all run on the main thread in sequence. TaskSystem exists and is good, but is used only for asset decode and skinning-pose work. There is no render thread, no parallel command recording, no async transfer queue, no compute queue — there are in fact no compute shaders in the project at all.

DoThe ordered, high-value steps: (1) parallelize IsoScenePreparer::prepare's per-face projection with parallelFor — it is embarrassingly parallel and currently the largest CPU block; (2) secondary command buffers recorded per-pass on workers; (3) a dedicated transfer queue for asset uploads, which also removes the editor's vkDeviceWaitIdle on texture repaint.
04

Vulkan correctness & hygiene

V1DebtDone

renderFinished semaphores are per frame-in-flight, not per swapchain image

Done. Done in Phase 0.

VulkanRenderer.hpp:190–196, maxFramesInFlight_ = 2 · VulkanRenderer.cpp:415–455 · VulkanSwapchainResources.cpp:641 imageCount = capabilities.minImageCount + 1

There are two renderFinished semaphores indexed by currentFrame_, but presentation waits on that semaphore for imageIndex, and the swapchain typically has three or four images. The inFlight fence proves the GPU work that signalled the semaphore finished; it does not prove the presentation engine's wait on it completed. With more images than frames in flight you can re-submit a signal on a semaphore a pending present is still waiting on.

This is the textbook Vulkan present-semaphore hazard. It usually works on desktop drivers with FIFO, which is exactly why it survives; it is undefined and shows up as intermittent validation errors or hangs, most often when the swapchain image count changes with window mode.

DoAllocate one renderFinished semaphore per swapchain image and signal renderFinished[imageIndex]. Keep imageAvailable per frame-in-flight, which is correct. If you later adopt VK_KHR_present_wait (already on your own "next improvements" list) this is a prerequisite.
V2Debt

Raw vkAllocateMemory in ten places, one allocation per image

VulkanResourceUtils.cpp:122–168 · plus VulkanUploadRing, VulkanFrameCapture, VulkanModelResources (×3), VulkanGeometryArena, VulkanSceneDescriptors, VulkanThumbnailPass, VulkanShadowPass, VulkanUiResources

There is no allocator. createImage does vkCreateImage → vkGetImageMemoryRequirements → vkAllocateMemory → vkBindImageMemory, so every texture is its own device allocation. maxMemoryAllocationCount is commonly 4096; the manifest cap of 64 textures keeps you far from it today, but the pattern does not scale and it fragments device memory. Buffers are better served — VulkanGeometryArena + GeometrySuballocator + VulkanUploadRing are genuinely good — the images just never got the same treatment.

Two smaller things sit in the same file: vulkanResources::subresourceRange and createImageView hardcode levelCount = 1, layerCount = 1, VIEW_TYPE_2D, so any mipped, arrayed or cube resource has to bypass the shared helpers (which is why VulkanShadowPass and VulkanModelResources hand-roll theirs).

DoAdopt VulkanMemoryAllocator, or extend the existing suballocator to images with a pooled heap. Either way, generalize createImage/createImageView to take mip and layer counts and a view type.
V3DebtDone

The skinning vertex shader copies a 16 KB struct per invocation

Done. Done in Phase 0.

shaders/skinned_model.vert.glsl:57 · GpuSkinning.hpp:26–34

struct SkinningInstance { mat4 palette[MAX_SKIN_JOINTS + 128]; mat4 modelFromSource; mat4 normalFromSource; };
// 258 mat4 = 16,512 bytes
SkinningInstance instance = skinning.instances[gl_InstanceIndex];   // ← whole-struct load

This emits an OpLoad of the entire 16 KB struct into function storage for every vertex. Good drivers scalarize it away because only a handful of members are read; that is not something to rely on, and it is a serious register-pressure hazard on the drivers that don't. The buffer sizing is also worth revisiting: 258 matrices × 256 instances × 2 frames ≈ 8.4 MB of palette storage, allocated at full size regardless of a model's actual joint count.

DoIndex members directly — skinning.instances[gl_InstanceIndex].palette[j] — and never bind the struct to a local. Separately, consider a packed palette with per-instance offsets so a 30-joint rogue does not reserve 258 slots.
V4DebtNext up

Descriptors: one set, one fixed 64-slot texture array, no descriptor indexing

Next up. Not started, and next in the queue. Descriptor indexing is also what unblocks the manifest reading a glTF’s own texture set, because the 64-slot ceiling is what makes that unaffordable today.

VulkanSceneDescriptors.cpp:41–140 · AssetManifest.hpp maxModelTextures = 64 (35 in use)

Everything lives in set 0: shadow map, scene color, a descriptorCount = 64 combined-image-sampler array, UI font, title background, scene depth, AO, lighting UBO, point-shadow cube array, and two storage buffers. There is no VK_EXT_descriptor_indexing, no UPDATE_AFTER_BIND, no PARTIALLY_BOUND — unused slots are padded with a 1×1 white fallback, and the whole set is rewritten when anything changes. Device selection rejects GPUs whose maxPerStageDescriptorSampledImages can't hold the array, so raising the cap narrows your hardware support.

Per-screen splat maps already consume one array slot each, so the ceiling is a content ceiling, not just a technical one.

DoEnable descriptor indexing with variable-count, partially-bound, update-after-bind bindings; split into frequency-based sets (per-frame / per-pass / per-material / per-draw). This is what makes bindless materials and streaming textures possible later.
V5DebtDone

Shaders compile unoptimized, targeting a Vulkan version you don't require

Done. Done in Phase 0.

CMakeLists.txt:199

"${GLSLC_EXECUTABLE}" --target-env=vulkan1.4 -DMODEL_TEXTURE_COUNT=${MODEL_TEXTURE_COUNT} \
  -DMAX_SKIN_JOINTS=128 -fshader-stage=${shader_stage} "${shader_source}" -o "${shader_output}"

Two things. DoAdd -O (and -g only for Debug), and set --target-env=vulkan1.3 to match VulkanDeviceContext. Cheap, low-risk, do it this week.
V6DebtDone

Anisotropic filtering is never requested

Done. Done in Phase 0.

VulkanModelResources.cpp:1634 .anisotropyEnable = VK_FALSE · VulkanDeviceContext.cpp:377–380 (feature not enabled)

Mipmaps are generated correctly by blit chain, but samplerAnisotropy is never requested as a device feature and every sampler runs isotropic. On the ground plane — exactly where the splat textures live and where the view is most oblique — that is visible blurring.

DoRequest the feature, gate on support the way wireframe already is, and pass the device's maxSamplerAnisotropy down to sampler creation. Apply it only to mipped, linearly-filtered textures so the point-sampled pixel-art atlases keep their crisp texels.
V7DebtPartly done

The SSAO is depth-only, pixel-scaled, and blurred without depth awareness

Partly done. The "AO modulates ambient rather than the whole composite" half landed inside F2b, using an ambient mask carried in the scene target’s alpha. The sampling rework — view-space normals, a world-unit radius, a bilateral blur — is untouched. See §11: F3c changed what that mask means.

shaders/ssao.frag.glsl · shaders/ssao_composite.frag.glsl · LightingConfig.hpp ssaoRadiusPixels, ssaoDepthRange

Four separate quality problems. It samples depth only, with no normals, so it cannot distinguish a crease from a depth step. Its radius is in pixels against non-linear depth with a fixed depthRange, so the AO scale drifts with camera distance and depth precision. The composite blur is a plain 5×5 box with no depth weighting, so occlusion bleeds across silhouettes. And it multiplies the fully lit image, darkening direct sunlight, where physically it should modulate ambient and indirect only.

DoReconstruct view-space position and normal from depth, express the radius in world units, blur bilaterally, run at half resolution, and apply it to the ambient term rather than over the composite. GTAO is the modern target and reuses all of that — but it wants a real view matrix first (C1).
05

Assets and the content path

The pipeline here is strong — manifest validation, atomic staging, priority scheduling, residency budgets. The formats are the weak part.

A1FoundationDone

The glTF loader is a regex-driven scanner over raw JSON

Done. Done in Phase 2, in two steps, with cgltf. See §11 for why cgltf rather than tinygltf, and what the swap was verified against.

GltfMesh.cpp:221–400 (hand-rolled scanner) · :310, 322, 334, 364, 374, 383, 393 (std::regex constructed per field lookup) · :1339 (bufferObjects.size() != 1)

Field access works by constructing a std::regex and running regex_search over the object's substring — per field, per object. std::regex construction is famously expensive, and a substring search can match a key nested inside a child object. Meanwhile nlohmann/json is already vendored and pinned in the project, used for the asset manifest, and simply not used here.

What the loader does not support: more than one buffer; sparse accessors; KHR_* extensions of any kind (including Draco and meshopt compression); glTF materials; TANGENT, COLOR_0, TEXCOORD_1 or JOINTS_1 attributes; morph targets; and animation interpolation modes — interpolation is never read, so STEP curves silently play as LERP and CUBICSPLINE curves fail the input.count != output.count check and throw.

DoYour own handoff already flags this ("consider switching to a proven GLTF library"). Take that advice — cgltf or tinygltf, both single-header and permissively licensed. It is a contained change with a large payoff: you inherit materials, extensions, compression and correctness in one step.
A2Throughput

Textures are RGBA8 only — no BCn, no KTX2, PNG decoded at runtime

ImageData.hpp:10–14 · VulkanModelResources.cpp:1557 (only R8G8B8A8_UNORM/_SRGB) · zero matches for BC/ASTC/ktx/basis

Every texture is a PNG on disk, decoded by stb_image into a full uncompressed std::vector<std::byte>, uploaded as RGBA8, and mipped on the GPU. That is roughly 4× the VRAM a BC7 equivalent would use, 6× for BC1 color, plus CPU decode time on every load. The residency budget is set to 256 MB of textures — with block compression that same budget holds four times the content.

DoCompress offline in sokoban_content_tool (which already validates and stages everything) to BC7/BC5/BC4 in KTX2 containers, with mips baked. Runtime then memory-maps and uploads without decoding. This also removes the CPU decode jobs from the load scheduler entirely.
A3Debt

One asset publishes per frame; nothing is ever evicted; there is no LOD or mip streaming

AssetLoadScheduler.hpp:38 maxPublicationsPerFrame = 1 · VulkanRenderer.cpp:316 publishReadyAssets(1) · handoff: "Loaded assets remain cached for the process lifetime; there is no eviction policy yet"

The scheduler is well designed — visible/prefetch priorities, bounded CPU jobs, residency caps, cancellable prefetch. Its granularity is whole assets, though: a 30-asset screen transition takes 30 frames (half a second) to fully populate, with geometry silently skipped by tileReadyForDraw until then. There is no mip-level streaming, no LOD chain, no eviction, and no partial residency.

DoRaise maxPublicationsPerFrame to a byte budget rather than a count. Add LRU eviction keyed off the residency caps that already exist. Mip streaming and mesh LOD come after BC7 + a real transform pipeline make them meaningful.
A4Debt

Per-frame heap allocation inside command recording

VulkanSceneRecorder.cpp:1115 std::vector<OpaqueDrawSortItem> orderedDraws; · OpaqueDrawSorter.hpp:14–20 (128-byte sort key) · requestAssets scans the whole manifest each frame

The recorder builds and sorts a fresh std::vector every frame, and sortOpaqueDraws returns another by value — despite FrameArena existing precisely for this. The sort key carries std::array<uint32_t, 29> fragmentState compared with <=>, so batching only merges draws agreeing on all 29 words of push-constant state, and the comparison itself is heavy. Separately, requestAssets loops over every model, animation and texture in the manifest on every drawFrame.

DoMove the sort scratch into the renderer as a reusable buffer (the ReusableScratchPool pattern is already in the codebase). Replace the 29-word key with a hashed material ID once materials are real objects rather than push-constant blobs.

07

Simulation, threading, and the shape of the world

S1Foundation

Variable timestep with no fixed simulation tick

Time.hpp:158–172 SimulationTiming::frameDelta · Application.cpp:424 const float dt = frameTimer_.tick(simulationTiming_);

The simulation runs on raw wall-clock delta, clamped to 100 ms, with a generation counter that discards the frame after a suspend. That is a careful implementation of a variable timestep — and it is correct for Sokoban, where moves are discrete and only the presentation interpolates. It is the wrong foundation for anything with physics, and there is no interpolation alpha to hand the renderer.

DoOnly if the game acquires continuous motion or physics: accumulator-driven fixed ticks (60 or 120 Hz) with a render-time alpha, and a decoupled presentation interpolation. Note this before adding physics, not after — retrofitting it means auditing every system that reads dt.
S2Throughput

The entire visible world is rebuilt from scratch every frame

RenderFrameBuilder.cpp — 2,555 lines · Application.cpp:1647, 1765 renderFrameArena_.reset() · RenderTypes.hpp:190–196 (capacities)

There is no scene graph, no ECS, no persistent renderable list. RenderFrameBuilder walks the level, the game state, the presentation state and the editor document and emits a complete flat description — up to 16,384 tiles and 65,536 iso faces — into a frame arena, every frame. IsoScenePreparer then projects and sorts all of it, every frame.

The arena is well built and the design is admirably stateless. But the cost is linear in authored world size with no way to skip unchanged regions, and there is no spatial structure for culling, streaming, queries, or physics to attach to.

DoIntroduce persistent renderable instances with dirty flags for static geometry (which is most of a board), keeping the per-frame rebuild for dynamic actors. That is the step that makes culling, LOD and streaming implementable — all three need something stable to reference.
S3Debt

TaskSystem: one mutex, one deque, no dependencies, no work stealing

TaskSystem.hpp:29–70 — "Tasks must not block waiting on other tasks (there is no dependency tracking or work stealing yet)"

Every task is a std::function<void()> pushed through a single std::mutex-guarded std::deque, with std::packaged_task and std::future per enqueue. That is three heap allocations and a lock per task. Fine for a handful of coarse asset jobs; it will contend badly the moment frame work is parallelized, which is exactly what §3 asks for.

DoPer-worker deques with work stealing, a fixed-size inline task payload instead of std::function, and explicit dependency edges (a counter per task plus a continuation list) so a job graph is expressible without blocking a worker.
S4DebtDone

A latent lifetime hazard around the frame arena

Done. Done in Phase 1.

Application.cpp:425 (update reads the previous prepared frame) → :551 prepareFrame(buildRenderFrame(...)) which calls renderFrameArena_.reset() internally · VulkanRenderer.cpp:744, 763, 882 read prepared.frameData.tiles

The previous frame's PreparedFrame holds a RenderFrameData whose arrays point into renderFrameArena_. pickDecoration and primaryPlayerBoundsToPixels read those tiles. This is currently safe only because every such read happens earlier in the loop than the reset() buried inside buildRenderFrame.

That invariant is invisible at both call sites and is exactly the kind of thing that breaks when someone moves the arena reset to the top of the loop — the natural place for it. Linux CI's ASan will never see it, because the render path doesn't build there.

DoEither double-buffer the arena (reset the one the previous prepared frame doesn't reference), or have prepareFrame take ownership of a deep copy of the small subset it needs to outlive the arena. Add a comment at reset() naming the invariant either way. Related: FrameArray's copy constructor silently converts arena storage into a heap std::vector — a quiet performance cliff worth a [[nodiscard]]-style warning or an explicit clone().

Engineering & CI

The test discipline is the strongest part of this project: 59 CTest suites, ASan + UBSan, clang-tidy, and a libFuzzer target for the profile codec, all gated in CI. That is better than most commercial codebases. Two gaps stand out for engine work specifically.

E1DebtDone

CI never builds with the compiler you ship, and never touches a GPU

Done. Done in Phase 1.

.github/workflows/required-tests.yml — runs-on: ubuntu-24.04 for all five matrix entries

All five jobs run on Ubuntu with GCC/Clang. Shipping is MSVC on Windows, so the compiler that produces the artifact is validated only on your machine. Your handoff already documents MSVC-only constructs that GCC and Clang reject (backslash includes, nested-type default initializers in default arguments) — that divergence runs both directions and nothing catches it.

There is also no rendering test of any kind beyond VulkanSmokeTests creating a device. No validation-layer run, no golden-image comparison, no GPU-timing regression gate. For a review whose findings are mostly in the renderer, that is the coverage that matters most.

A sequenced plan

Every step below is one of the findings above, named by its ID, in the order it should be picked up. Ordering is the whole point: each phase makes the next one cheap, and doing them out of order means writing the same code twice. Phases are independently schedulable; steps within a phase are not.

Where this standsPhases 0 and 1 are complete. Phase 2 is complete except for F2c (a real tonemap curve and a user-facing exposure control), the sampling half of V7, and F4. The next step is V4 out of Phase 3, pulled forward deliberately: descriptor indexing removes the 64-texture ceiling, and that ceiling is what makes it unaffordable to let the manifest read a glTF's own normal, metallic-roughness, emissive and occlusion maps. That map work follows immediately after V4 and finishes what F3 started. Implementing this plan turned up several places where the review was wrong about its own subject matter; those corrections are summarised in §11 and worth reading before trusting any estimate here.

10

What not to touch

A review that only lists problems misrepresents the codebase. Several parts of this engine are done properly and should survive every phase above intact.

Keep as-is
  • Frame resource lifetime management. FrameResourceTracker, RendererReconfigurationQueue, generation-tagged retirement, replacement resources built before publication, retired bundles held until every referencing fence completes. This is how it should be done and it is rare to see it done at all.
  • Buffer memory. VulkanGeometryArena + GeometrySuballocator + a persistently-mapped VulkanUploadRing with fence-guarded reservations. Real engine technique, tested in isolation.
  • The asset scheduler. Visible/prefetch priorities, bounded concurrency, residency budgets, cancellable prefetch, per-frame publication throttling, failures retained and reported without interrupting play.
  • Headless separation. Rules, LevelEditor, SplatCanvas, IsoScenePreparer, OpaqueDrawSorter, AssetLoadScheduler all testable without SDL or Vulkan. This is why 59 suites are possible.
  • The content pipeline. Manifest validation, path containment, temp-directory staging with atomic replacement, stale-file removal, a runtime that only ever reads the staged tree.
  • Diagnostics. GPU timestamp profiler, CPU/GPU frame-time telemetry with p95, debug object names, pipeline cache, device-suitability gating with actionable messages, crash diagnostics, atomic saves with a 26-format migration chain.
  • Skeletal animation. GPU skinning, crossfades, timeline events with named dependencies, skeleton-node attachments. Genuinely the most modern subsystem in the engine.

The honest summary: you have built the operations half of a shippable engine — packaging, validation, telemetry, tests, tooling, content staging — to a standard most projects never reach, on top of a rendering core that was scoped precisely to an isometric tile board. The work ahead is not cleanup. It is replacing the geometry and shading path with one that has a camera, a material, and range, and then letting the good infrastructure you already have carry it.

Corrections from implementation

Phases 0 through 2 were built against this document. Several things it asserted turned out to be wrong, and one turned out to be right for the wrong reason. They are recorded here rather than quietly edited away, because each was found the expensive way and the reasoning that produced them is worth distrusting again.

C1Corrected

The clip-space clamp was the real defect, not the missing camera

IsoScenePreparer::projectIsoPoint · calculateIsoLayout

Because quads were projected on the CPU and pushed as clip-space vertices, there was no near or far clipping to rely on, so projectIsoPoint clamped z into [0, 1]. Anything past the far plane did not vanish; it arrived at exactly 1.0, sharing that depth with every other such surface. The depth range was derived from the camera-fit geometry alone, and every gameplay frame sets an explicit cameraExtent, so any tile a designer had marked as scenery landed on the far plane.

Two bugs came out of that one fact. T2's sort flip turned the far row of a board inside out, because a tie under LESS_OR_EQUAL goes to whichever drew last. It was reported as a back-face culling bug and is not — the culling toggle made no difference. Then VK_COMPARE_OP_LESS, tried as the fix, made the row vanish outright, because the depth buffer clears to exactly 1.0.

CorrectionThe on-screen fit and the depth range are different questions and must be computed separately: the fit stays authored, the depth range covers every drawn tile. This is a prerequisite for T2, not a consequence of C1, and reordering opaque geometry is unsafe until it holds.
T1Corrected

"Falls out of C1 almost for free" was wrong

shaders/triangle.frag.glsl — 8 pipelines, 41 per-draw references

The plan assumed the transform pipeline was what blocked instancing. It was not. triangle.frag is shared by tiles, UI, static models and skinned models, and reads its per-draw parameters from push constants in 41 places; ground_splat.frag adds 29, water.frag 41, mirror_energy.frag 17. Instancing tiles means moving that data into a buffer, and every other consumer of the block has to follow it — models included, because they share the fragment shader.

CorrectionT1 is a per-draw data move, which is F4's problem wearing a throughput hat. It was landed in two steps — move the data with the draw count unchanged, then merge runs — precisely so the first step either rendered identically or was plainly broken. Anything else that depends on the über-shader should expect the same surprise.
C1Corrected

Not every quad has a world position

shaders/triangle.vert.glsl · UI, the top-down 2D board, the grid overlay

§1 describes the CPU projecting "every vertex", which is true of the scene and false of the interface. The UI and the 2D board author their quads directly in clip space and share the same vertex shader. Giving that shader a camera projected them too, and the entire interface left the screen at once — which presents as a window that never finished loading, not as a transform bug.

CorrectionA quad's corner carries which space it is in. The tidy version is a separate screen-space pipeline, which belongs with F4.
C1Corrected

The 256-byte block was not freed, and the shadow pass keeps it

shaders/water.frag.glsl · shaders/shadow.vert.glsl

Deleting the shadow-space copy of the corners was supposed to return 64 bytes. It did not: water.frag was already using those bytes for its border and ripple parameters — an instance of the slot-reuse §1 complains about, one layer deeper than it looked. The block later moved into a storage buffer wholesale under T1, which is the actual answer to it being full.

Separately, the shadow pass cannot take a camera from a uniform: it has one per sun and six per point light. Its pipelines still receive CPU-projected clip-space corners, and that is correct rather than unfinished — nothing in a shadow pass reads a world position.

F2Ordering to reconsider

V7 may want to come forward into F2

Phase 2 — F2 before V7

The plan puts V7 after F3, on the grounds that ambient occlusion needs a correct ambient term to modulate. That is right, but it means moving the composite twice: F2 has to reorder it anyway so that the UI composites after tonemapping, and AO wants to apply pre-tonemap for the same reason it wants to apply to ambient.

ConsiderPull the "AO modulates ambient rather than the composite" half of V7 forward into F2, and leave the sampling rework - view-space normals, world-unit radius, bilateral blur - where the plan has it. The two halves are independent.
T2Right, wrong reason

Tile faces were never perspective-correct

VulkanSceneRecorder — drawFace, drawGroundSplatFace

Face quads were pushed already divided, with w = 1, so their attributes interpolated affinely. The review treated the CPU projection purely as a flexibility problem; it was also a correctness one. Ground-splat UVs and grid lines on large quads were subtly wrong, and the splat shader's "global origin" was a normalised device coordinate wearing a world-space name. Both are fixed by C1 as a side effect.

A1Corrected

cgltf, not tinygltf — and the choice was not close

Phase 2 — A1

The finding offers "cgltf or tinygltf" as if either would do. For this engine they are not equivalent. The loader is called from worker threads, has to round-trip non-ASCII Windows paths, and is held behind a header that deliberately names no library type. cgltf is a single C99 header with a caller-supplied file-read callback, which satisfies all three; tinygltf pulls in a C++ JSON dependency and owns its own I/O. A third option the document does not mention, fastgltf, is a better long-term fit — SIMD parsing, first-class GLB and extension support — and is pinned in HANDOFF.md with the three triggers that should make someone revisit it.

Method worth reusingThe swap was verified by a differential digest harness that loads every model, skinned mesh, animation and pose the manifest reaches — 734 jobs — and hashes the result field by field, so one binary builds against both the old and the new vertex layout. Every step of A1 and F3 was held to byte-identical output on it, which is what made it safe to change the loader and the vertex format underneath a running game.
F3Corrected

The material model has to reach the shader before a BRDF can use it

Phase 2 — F3

The finding reads as one step: parse materials, move to GGX. In practice the parsing was the easy half. A glTF material is per-primitive, a draw covers a whole model, and this engine's manifest — not the glTF — decides what texture a model uses. So the material had to become a GPU storage buffer indexed by a per-draw base plus a per-vertex material index before any BRDF could read a roughness. That is three landed steps (F3a vertex substrate, F3b material model then material buffer, F3c the BRDF), not one.

The trap in the middle: of the manifest's 36 models, 29 declare material.mode: "texture", six declare nothing, and one uses primitive-materials. Reading the material only where glTF materials are declared would have given 35 of 36 models no metallic and no roughness — a physically based renderer lighting one conveyor belt. The material read had to be widened to every draw first, with a reserved fallback entry for draws that have no model behind them.

Consequence for F4This document says F4 is worth doing "once F3 has made the branch count worse". It has: triangle.frag.glsl went from 382 lines to 576, and now carries a full Cook-Torrance implementation alongside the UI font, the title art and the rounded-rect SDF. F4 is the largest remaining Foundation item and the case for it is stronger than when this was written.
V7Right, wrong reason

The ambient mask is a per-pixel ratio, and a BRDF swap redefines it

Phase 2 — V7 inside F2b, revisited by F3c

Pulling V7's "AO modulates ambient" half forward into F2 was the right call, and it works: the scene target's alpha carries the share of a pixel's light that came from the ambient term, and the composite scales occlusion by it. What was not obvious is that this ratio is a function of the BRDF. F2b defined it as "diffuse only, on both sides", on the reasoning that occlusion has no business scaling a direct reflection.

F3c broke that definition without touching the composite. Cook-Torrance introduces an ambient specular term — the environment stand-in that keeps a metal from going black — which is ambient light by construction but sits on the specular side of the split. Left out of the ratio, a metallic surface reported a smaller ambient share than it had, and a fully metallic one computed zero over zero and took no occlusion at all. The mask is now "ambient contribution over total contribution", with direct light in the denominator only.

For whoever does the rest of V7Two shaders write this channel — triangle.frag.glsl and ground_splat.frag.glsl — and they must agree on what it means. They did not until F3c: one weighed the ratio against the albedo and the other against the light alone, which drift apart whenever an albedo is saturated, because the sun and the ambient term do not share a spectrum. Any further change to either lighting path has to re-check this ratio.
