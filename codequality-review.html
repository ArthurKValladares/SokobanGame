Sokoban Engine Audit

The engine is in genuinely good shape. Resource lifetimes are correct, Vulkan return codes are checked almost everywhere, the comments explain why rather than restating the code, and CI runs Debug, Release, ASan, UBSan, clang-tidy, fuzzing and a headless validation pass. What follows is therefore not a list of things that are broken. It is a list of places where the code is harder to change than it needs to be — most of them concentrated in one theme: the CPU ↔ GPU contract is maintained by hand in up to eight places at once, and nothing checks that the copies agree.

A

Correctness and latent defects

Nothing here misbehaves in the shipping configuration today. Each item is a guard that has fallen out of step with the code it protects, or a failure mode that is handled more harshly than it needs to be.

Major Outdated guard

The static-mesh guard still asks “is this the player?”, not “is this skinned?”

src/engine/render/VulkanModelResources.cpp:2667 assets/manifest.json 
// gpuMeshForModel — the safety net for "this model has no static mesh"
if (model.isCube() ||
    model == manifest_->playerModel() ||
    model.index() >= models_.size()) {
    throw std::runtime_error("Render model does not have a static GPU mesh");
}

Everywhere else in the class, “this model is skinned” is decided by manifest_->model(model).geometry == ModelGeometry::Skinned (modelUsesGpuSkinning, line 176). This one guard instead compares against the player model by identity — an assumption from when the player was the only skinned mesh. The manifest already declares two skinned models, Rogue and Barbarian.

It produces no wrong result today only because meshForTile branches on geometry first and never reaches this line for a skinned model. But the guard is the last line of defence, and half of it is already blind. If the routing above it ever changes, a skinned model walks straight past the net and reads an empty GpuMesh.

Replace the identity test with the same geometry test the rest of the class uses. Better still, give ModelSlot a resolved geometry field at publication so no call site re-derives it from the manifest at all.
Major Failure handling

Content-driven budget overflow terminates the process

VulkanModelResources.cpp:1467 VulkanModelResources.cpp:1499 VulkanRenderer.cpp:404 src/main.cpp:134

updateAnimations throws std::runtime_error("GPU skinning instance budget exceeded") when more than 256 skinned instances appear in one frame, and writeDrawInstance throws "Draw instance buffer is exhausted or invalid" the same way. Both are called from inside drawFrame, whose only catch is for VulkanError — so a plain runtime_error passes straight through, unwinds Application::run, and lands in main’s fatal handler: dialog, minidump, exit 1.

That is the correct response to a device loss. It is a harsh response to “a level author put 257 enemies on screen”, which is a bounded, recoverable, purely visual condition. The renderer already has a well-designed vocabulary for degrading gracefully — nonresident textures fall back, unavailable models are counted in RenderStats::unavailableModels and skipped. These two limits are the only places that reach for termination instead.

Return a sentinel (or std::optional) instead of throwing, skip the instance, and surface the overflow through RenderStats the same way unavailableModels already is. Log once per frame rather than per instance so a full board does not flood the log.
Major ODR hazard

A build flag that gates class members silently defaults itself to zero

src/engine/Application.hpp:41 src/engine/Application.hpp:205 src/engine/DebugUi.hpp:7 src/main.cpp:17 + 5 more files 
#ifndef SOKOBAN_ENABLE_DEBUG_UI
#define SOKOBAN_ENABLE_DEBUG_UI 0
#endif
...200 lines later, inside class Application:
#if SOKOBAN_ENABLE_DEBUG_UI
    std::unique_ptr<ApplicationTools> tools_;
#endif

Eight files carry this fallback, and two of them are headers that use the macro to add or remove a data member. Any translation unit that includes Application.hpp without the compile definition gets a different sizeof(Application) and different member offsets from the rest of the program — a silent ODR violation that links cleanly and corrupts memory at runtime.

It is latent, not live: all three targets that reach these headers do set the definition today. The problem is that the fallback is precisely what turns “someone forgot the definition on a new target” from a compile error into a memory-corruption bug. That is the wrong default for a flag with ABI consequences.

Delete all eight fallbacks. Replace them with #ifndef SOKOBAN_ENABLE_DEBUG_UI
#error "SOKOBAN_ENABLE_DEBUG_UI must be defined by the build"
#endif, or generate a SokobanConfig.hpp with configure_file and include that instead of relying on a command-line macro at all.
Moderate Coupled constants

Frames in flight and the skinning frame count must agree, and nothing says so

VulkanRenderer.hpp:290 render/GpuSkinning.hpp:16 VulkanModelResources.cpp:1477

VulkanRenderer::maxFramesInFlight_ is 2 and gpuSkinningFrameCount is 2, declared in different headers by different owners. beginAnimationFrame throws std::out_of_range if the frame index exceeds the second one, so raising frames-in-flight to 3 is a runtime crash on the first frame rather than a compile error.

This is out of character for the file: VulkanRenderConstants.hpp carries eleven static_asserts pinning GPU struct sizes, alignments and every field offset. The one invariant that couples two independent headers is the one left unasserted.

static_assert(gpuSkinningFrameCount == VulkanRenderer::maxFramesInFlight_), or make one derive from the other.
Moderate Constant drift

The point-shadow near plane exists three times, as three unrelated literals

render/LightingConfig.hpp:52 shaders/triangle.frag.glsl:274 shaders/ground_splat.frag.glsl:189

config::pointShadowNearPlane = 0.05f drives the CPU-side projection in VulkanSceneRecorder::projectPointShadow. Both fragment shaders that unproject that depth hard-code const float nearPlane = 0.05; locally. They agree today. If the C++ constant is ever tuned, point shadows silently shift on every lit surface and the symptom — a global bias error that looks like a shadow-acne regression — points nowhere near the change.

Push it through SceneFrameUniform alongside the other frame-wide lighting data, or (see B1) emit it into a generated GLSL constants header that both shaders include.
Moderate Divergent paths

Runtime-appended models skip the descriptor remap the startup path applies

VulkanModelResources.cpp:2506 VulkanModelResources.cpp:236

create() routes every model’s texture dependencies and material bindings through textureCatalog.descriptorIndex() and remapBindingTextures(), because manifest textures live at the low end of the descriptor heap and glTF-discovered maps live at the high end. syncManifestModels() — the Debug decoration-authoring path — pushes definition.textureIndex raw, with no remap at all.

It happens to be correct, because descriptorIndexForLogicalTexture is the identity function below manifestTextureCount_ and editor models only reference manifest textures. But the correctness depends on an invariant stated nowhere, in a function that looks like it simply forgot a step. The same function also builds bindings with base colour only — no normal, metallic-roughness, emissive or occlusion handle — so editor-appended models silently get a lesser material path than manifest-loaded ones.

Call remapBindingTextures unconditionally so both paths read the same, and either extend the binding construction to the full map set or add a comment stating that editor decorations are deliberately base-colour only.

Minor Error handling

Three vkDeviceWaitIdle calls drop their result

VulkanDeviceContext.cpp:224 VulkanModelResources.cpp:2563 VulkanThumbnailPass.cpp:76

Every other Vulkan entry point in src/engine/render is wrapped in vkCheck, or explicitly discarded with (void) where failure is genuinely uninteresting. These three do neither, so VK_ERROR_DEVICE_LOST at a wait point is swallowed and the next operation fails somewhere less informative.

B

The CPU↔GPU contract is maintained by hand

This is the highest-leverage theme in the audit. The handoff is rightly proud that GpuMaterial’s size, alignment and every field offset carry compile-time assertions and were verified against SPIR-V disassembly. That rigour stops at the shader source, where the same structures are retyped by hand and nothing checks them.

Major Duplication

The shared GPU structs are retyped in every shader that uses them

DeclarationC++ ownerHand-copied into
struct DrawInstanceGpuDrawInstance (256 B)8 shaders
uniform SceneFrameSceneFrameUniform (544 B)6 shaders
struct PointLightDataPointLightUniform (48 B)6 shaders
struct MaterialGpuMaterial (112 B)2 shaders

Adding one vec4 to GpuDrawInstance means editing eight .glsl files correctly and in the same order. Getting it wrong in one of them produces a shader that compiles, validates, and reads the wrong bytes. The static_asserts catch the C++ half of the contract and nothing catches the GLSL half.

The build already uses glslc, which supports #include via GL_GOOGLE_include_directive and -I. There is no technical obstacle here — only that the mechanism was never turned on.

Add shaders/include/ with SceneFrame.glsl, DrawInstance.glsl and Material.glsl; pass -I shaders/include in the CMake shader rule and add #extension GL_GOOGLE_include_directive : require to the modules. This removes roughly 250 lines of copied declarations and turns four ABIs into four single sources of truth.
Major Duplication

The shadow sampling functions are duplicated verbatim across two shaders

shaders/triangle.frag.glsl:230–307 shaders/ground_splat.frag.glsl:145–210

shadowFactor, pointShadowWorldDistance and pointShadowFactor — including the 3×3 PCF loop, the five-tap cube kernel, the grazing-angle bias ramp and the near-plane literal — are byte-identical in both files. A window-based comparison finds 47 shared 12-line spans between them, roughly 60 duplicated lines of shadowing logic plus the declaration blocks above.

Two shaders currently write the ambient mask and the handoff makes it an explicit invariant that they “must calculate the same semantic ratio”. Right now that invariant is upheld by remembering to edit both files.

Same mechanism as B1: move them to shaders/include/Shadowing.glsl. The invariant then holds by construction instead of by discipline.
Major Fragile encoding

One vec4 lane carries three unrelated meanings depending on the draw

VulkanSceneRecorder.cpp:1733, 1780, 1881, 1974, 2077, 2257, 2458 shaders/triangle.frag.glsl:202, 217, 79, 645

Seven call sites write GpuDrawInstance::materialOptions, each with a different meaning per lane, and the fragment shader reads several of those meanings without knowing which draw produced it:

LaneWritten asRead as
.x blur flag · face world-origin X · camera X “blur behind” predicate
.y grid size X · UV rect width · belt scroll offset grid-mask gate and material UV scroll
.z grid size Y · UV rect height · manifest texture index grid-mask gate and texture selector
.w ±blur radius (sign = editor preview) · ±water mode · animation time blur radius, dither predicate and highlight pulse clock

.y is the sharpest case: gridMask() treats it as a grid dimension and bails when it is <= 0.0, while materialTextureUv() treats the same lane as a scroll offset added to uv.y. A model draw that ever wanted both would have to choose. textureOptions.y is likewise both a one-based procedural texture handle and an editor-highlight enum, separated only by the draw.gridColor.w < 0.0 flag — a boolean smuggled into an alpha channel as a negative number.

Two options, in increasing order of effort. Cheap: document the union explicitly in VulkanRenderConstants.hpp the way passData already is, naming which draw kind claims which lane. Better: follow the precedent GpuMaterial already set — add a uvec4 of explicit integer lanes carrying a draw-kind tag and the flags, so the shader branches on a named kind instead of inferring it from the sign of an alpha channel.

C

Size, structure and readability

The codebase is well modularised at the file level — 279 files with clear ownership boundaries. The pressure is inside a handful of specific functions and one class.

Major God object

VulkanModelResources owns eight things at once

VulkanModelResources.cpp — 2,710 lines VulkanModelResources.hpp — 557 lines

3,267 lines, 40 private members and 60-odd methods covering: mesh loading and upload; texture loading, format selection, mip generation and upload; animation clip loading; the skinning palette buffer; the draw-instance buffer; the material buffer and its free-list allocator; two residency budgets with eviction and fence-owned retirement; and the descriptor-heap index mapping. Any one of those is a reasonable class.

The consequences are visible in the file: the load-state machine (Unrequested → Queued → Loading → CpuReady → Uploading → Ready) is implemented three times, once per asset kind, with each copy slightly different — publishModel recurses into itself, publishTexture falls through, publishAnimation has no CPU-ready phase at all. A reader has to hold all three in their head to be confident about any one.

The natural seams are already visible in the member list. Split out ModelGeometryStore (models, meshes, bounds, materials), TextureHeap (slots, definitions, uploads, descriptor mapping) and ResidencyBudget (budgets, victim selection, retirement) — the last is the easiest first cut because makeModelResident and makeTextureResident are already the same algorithm twice. Then template the shared load-state machine over the slot type so the three copies collapse into one.

Duplication

Textual duplication is low — an exact-match scan across all 279 source files finds only two 20-line clusters. The duplication here is structural: near-identical code that differs by a type or a field name, which a text search will never surface but which still has to be edited in lockstep.

Moderate Structural

Moderate Structural

The residency and retirement algorithms are written twice

VulkanModelResources.cpp:1147 VulkanModelResources.cpp:1204 :1279 :1291

makeModelResident and makeTextureResident are 50-line functions that differ only in which vector they scan and which pair of byte counters they touch: same early-out ladder, same “a retirement is already pending” guard, same LRU victim search protecting the current visible stamp, same eviction loop, same closing predicate. retireModel and retireTexture are the same shape again.

Extract a ResidencyBudget holding { budget, resident, retiring, peak } and a template makeResident(slots, protectedIndex, bytes, budget) constrained on the slot having state, gpuBytes and lastRequested. This is the highest-value single extraction in the file and the natural first step toward splitting the class (see C1).
Moderate Reinvention

ModelBounds reimplements Aabb

VulkanModelResources.hpp:91 VulkanModelResources.cpp:137 src/engine/Geometry.hpp:29

Geometry.hpp provides Aabb with an inverted default sentinel, valid(), expand(), merge(), aabbFromPoints(), center(), extents(), transformed() and frustum intersection — and the handoff records it as completed shared infrastructure (F1). VulkanModelResources instead declares its own { Vec3 minimum, Vec3 maximum, bool valid } and boundsOf() hand-writes the six min/max comparisons that aabbFromPoints already performs.

The cost is visible downstream: VulkanRenderer::pickDecoration has to expand ModelBounds into eight corners by hand, and the handoff notes that model-backed tiles “fail open because their retained unit transform is not yet the loaded mesh’s true local AABB” — a gap that closes more naturally when both sides speak the same type.

Delete ModelBounds; return Aabb. Replace boundsOf with aabbFromPoints over a positions view. The eight-corner expansion in pickDecoration and primaryPlayerBoundsToPixels then becomes one shared corners(Aabb) helper.
Moderate Coupled maths

The isometric projection has two independent implementations

IsoScenePreparer.cpp:50 IsoScenePreparer.cpp:84 Math.hpp:713

projectIsoPointToClip computes the projection by hand; isoClipFromView builds the same projection as a Mat4 through mat4PerspectiveOffCenter. They agree term for term today — I checked all four components — but they are maintained separately and consumed by different subsystems: the hand-written one drives CPU face projection and picking, the matrix drives frustum culling and SSAO unprojection.

If they ever drift, culling rejects geometry the rasteriser would have drawn, or SSAO samples land in the wrong place — both of which present as visual artefacts far from the edit that caused them. There is a test that compares isoClipFromWorld against projectIsoPoint at IsoScenePreparerTests.cpp:564, which is good; it is worth being explicit that this test is the only thing holding the two together.

Either derive one from the other (projectIsoPointToClip becomes transform(isoClipFromView(...), toVec4(viewPoint, 1)) with the near-plane clamp applied first), or add a comment at both sites naming the test that pins them together.

Minor Boilerplate

Repeated preambles in the renderer’s public surface

VulkanRenderer.cpp:865, 899, 929 VulkanRenderer.cpp:547–572 VulkanSceneDescriptors.cpp:277
  • pickIsoGridCell, pickIsoGroundPoint and pickDecoration each repeat the same eight-line preamble: check the view mode, fetch the output extent, reject a zero extent, map the pointer, reject a negative result. A single std::optional<Vec2> mapPickPoint(frame, pixel) covers all three.

Handoff item 0.3 calls for “a small .gitattributes policy” and normalised line endings “in its own commit, never mixed with semantic changes”. The sibling clean-up in that item — deleting GpuModelInstance.hpp — is done; this half is not, and the working tree has drifted further:

Mixed endings inside a single file are the costly case: an editor that normalises on save rewrites hundreds of untouched lines, so the next real change arrives as a 900-line diff that git blame can no longer see through. Two of the worst-affected files — RenderFrameBuilder.cpp and VulkanSwapchainResources.cpp — are also two of the largest. .github/workflows/required-tests.yml is affected too.

.gitattributes with * text=auto eol=lf and binary exclusions, then git add --renormalize . as a single commit touching nothing else, and a CI step that fails on a non-empty git diff --exit-code after renormalising. Do this before the refactors above, not after — otherwise every one of them lands as an unreviewable diff.
Moderate CI gate

Warnings are enabled everywhere and gated nowhere

CMakeLists.txt:262

sokoban_enable_warnings sets /W4 /permissive- on MSVC and -Wall -Wextra -Wpedantic otherwise, applied consistently to every target — but never /WX or -Werror. Six CI jobs build this project on two toolchains, so the enforcement infrastructure is already there and unused. A warning introduced today goes unnoticed until it is one of hundreds.

Add a SOKOBAN_WARNINGS_AS_ERRORS option, default OFF for local builds and ON in the CI matrix. Turning it on will surface a batch of existing warnings; fix or suppress them once, then it stays clean for free.
Moderate Static analysis

clang-tidy runs with one check group enabled

CMakeLists.txt:296

The configuration is -checks=-*,clang-analyzer-* with -warnings-as-errors=*. The comment explains the intent — keep it a high-signal gate, leave broad style checks to a separate policy — and that reasoning is sound for readability-* and modernize-*.

It leaves out two groups that are not style, though. bugprone-* would have flagged several items in this report directly, and performance-* catches unnecessary copies in a codebase that passes a lot of vectors and std::filesystem::path by value. Both are low-noise and produce real defects, not opinions.

-checks=-*,clang-analyzer-*,bugprone-*,performance-*, with specific -bugprone-easily-swappable-parameters style opt-outs if the noise is not worth it. Add a .clang-tidy file so the configuration is visible to editors, not just to CMake.

Minor Build config

CMake regex-parses a C++ header to build the shader list

CMakeLists.txt:189–228

The build reads ShaderCatalog.hpp, extracts the quoted filenames and the declared array size with regexes, and errors if they disagree. The validation is careful and the error messages are good — but the coupling is a string-matching dependency on C++ source formatting. Reformatting the header breaks the build in a way that has nothing to do with shaders.

Note this is the same shape as the MODEL_TEXTURE_COUNT header scraping that handoff packet 2.3 removed. One instance survived.

Invert it: list the shaders in CMake and generate ShaderCatalog.hpp with configure_file. CMake then owns the list, C++ consumes it, and the two cannot disagree.
Minor Consistency

No formatting configuration exists

There is no .clang-format and no .editorconfig. The house style is actually very consistent — four-space indent, Allman braces on functions, K&R inside them, trailing-comma designated initialisers, ~80 column wrap — which means it is being maintained by hand and by review. That works until it doesn't, and it is what makes the unindented try block in drawFrame possible.

Generate a .clang-format that reproduces the current style (clang-format --style=... --dump-config against a representative file, then hand-tune), and land the reformat in the same commit as the line-ending normalisation so there is exactly one noisy diff in the history rather than two.
✓

What is already working, and should not be touched

  • Resource lifetime is genuinely correct. Fence-owned retirement with a submitted-frame bitmask, per-swapchain-image present semaphores with the reasoning written out in the header, a present-queue wait only when a retired swapchain has no in-flight users, and stable material ranges that return to a coalescing free list only after their frames clear. This is the hardest part of a Vulkan renderer to get right and it is right.
  • The comments explain reasoning, not mechanics. “The near plane uses row 2 alone rather than row2 + row3 because Vulkan’s clip volume is 0 ≤ z ≤ w” and the note about not “tidying up” the shadow depth row are the kind of comments that save a future reader a day. This is rare and worth protecting through every refactor above.
  • Vulkan return codes are checked systematically. A sweep of src/engine/render found three unchecked calls out of hundreds, all vkDeviceWaitIdle, all in teardown or editor paths.
  • CI is stronger than most projects this size. Debug, Release, ASan+UBSan, clang-tidy, a fuzz target for profile decoding, MSVC and Linux, plus a headless run that turns Vulkan validation errors into a non-zero exit code. That last one is the difference between “validation is enabled” and “validation is enforced”.
  • GPU ABI discipline where it is checked. Eleven static_asserts pinning GpuMaterial’s size, alignment and every field offset, verified against SPIR-V disassembly. Section B is not a criticism of this — it is an argument for extending the same standard to the shader side.
  • Ownership boundaries are clear at the file level. 279 files with descriptive names and one job each. The problems in section C are about a handful of functions, not about the architecture.

Where I would start

This order is deliberate: the first step makes every later diff readable, and the second removes the mechanism that would otherwise let the later ones introduce a silent ABI mismatch.

  1. Normalise line endings and add .gitattributes. G1 — one commit, no semantic change, with a CI guard. Every refactor below produces a reviewable diff afterwards and an unreviewable one before. This is the open handoff item 0.3.
  2. Turn on #include for shaders and move the shared declarations. B1, B2 — deletes about 250 lines of copied struct declarations and 60 lines of duplicated shadow code, and converts four hand-maintained ABIs into four single sources of truth. Purely mechanical, verifiable with spirv-dis on the before and after.
  3. Fix the three correctness items. A1 (the skinned-model guard), A3 (the ODR fallback) and A4 (the frames-in-flight assert). All three are small, none needs a design decision, and each removes a way for a future change to fail silently.
  4. Extract ResidencyBudget from VulkanModelResources. D3 — this is the highest-value single extraction in the renderer, it collapses two 50-line algorithms into one, and it is the natural first cut toward C1. The existing FrameResourceTrackerTests coverage makes it safe to do.
  5. Introduce the shared test harness. E1 — do it before the larger refactors, so that when a test fails during them you get an expression and a line number instead of a hand-written label.
  6. Then the structural work. C1 (splitting the class), C2 (the long functions), D1 (the face-draw payload) and B3 (the overloaded lanes). These are larger and benefit from everything above being done first.
