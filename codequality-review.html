Sokoban Engine Audit

The engine is in genuinely good shape. Resource lifetimes are correct, Vulkan return codes are checked almost everywhere, the comments explain why rather than restating the code, and CI runs Debug, Release, ASan, UBSan, clang-tidy, fuzzing and a headless validation pass. What follows is therefore not a list of things that are broken. It is a list of places where the code is harder to change than it needs to be — most of them concentrated in one theme: the CPU ↔ GPU contract is maintained by hand in up to eight places at once, and nothing checks that the copies agree.

Resolved Was: major · outdated guard Outdated guard

The static-mesh guard still asks “is this the player?”, not “is this skinned?”

src/engine/render/VulkanModelResources.cpp:2667 assets/manifest.json 
// gpuMeshForModel — the safety net for "this model has no static mesh"
if (model.isCube() ||
    model == manifest_->playerModel() ||
    model.index() >= models_.size()) {
    throw std::runtime_error("Render model does not have a static GPU mesh");
}

Everywhere else in the class, “this model is skinned” is decided by manifest_->model(model).geometry == ModelGeometry::Skinned (modelUsesGpuSkinning, line 176). This one guard instead compares against the player model by identity — an assumption from when the player was the only skinned mesh. The manifest already declares two skinned models, Rogue and Barbarian.

It produces no wrong result today only because meshForTile branches on geometry first and never reaches this line for a skinned model. But the guard is the last line of defence, and half of it is already blind. If the routing above it ever changes, a skinned model walks straight past the net and reads an empty GpuMesh.

Replace the identity test with the same geometry test the rest of the class uses. Better still, give ModelSlot a resolved geometry field at publication so no call site re-derives it from the manifest at all.

Done. The guard now asks modelUsesGpuSkinning(model) — the same geometry test the rest of the class uses — instead of comparing against the player by identity.

The replacement is provably a superset of what it replaced, not a behavioural change: AssetManifest.cpp:583 rejects any manifest whose player model is not skinned, so “is the player” already implied “is skinned”. The old guard therefore caught Rogue and missed Barbarian, which is skinned too and carries the enemy role. The new one catches both, and every skinned model added later.

Major Failure handling

Content-driven budget overflow terminates the process

VulkanModelResources.cpp:1467 VulkanModelResources.cpp:1499 VulkanRenderer.cpp:404 src/main.cpp:134

updateAnimations throws std::runtime_error("GPU skinning instance budget exceeded") when more than 256 skinned instances appear in one frame, and writeDrawInstance throws "Draw instance buffer is exhausted or invalid" the same way. Both are called from inside drawFrame, whose only catch is for VulkanError — so a plain runtime_error passes straight through, unwinds Application::run, and lands in main’s fatal handler: dialog, minidump, exit 1.

That is the correct response to a device loss. It is a harsh response to “a level author put 257 enemies on screen”, which is a bounded, recoverable, purely visual condition. The renderer already has a well-designed vocabulary for degrading gracefully — nonresident textures fall back, unavailable models are counted in RenderStats::unavailableModels and skipped. These two limits are the only places that reach for termination instead.

Return a sentinel (or std::optional) instead of throwing, skip the instance, and surface the overflow through RenderStats the same way unavailableModels already is. Log once per frame rather than per instance so a full board does not flood the log.

A build flag that gates class members silently defaults itself to zero

src/engine/Application.hpp:41 src/engine/Application.hpp:205 src/engine/DebugUi.hpp:7 src/main.cpp:17 + 5 more files 
#ifndef SOKOBAN_ENABLE_DEBUG_UI
#define SOKOBAN_ENABLE_DEBUG_UI 0
#endif
...200 lines later, inside class Application:
#if SOKOBAN_ENABLE_DEBUG_UI
    std::unique_ptr<ApplicationTools> tools_;
#endif

Eight files carry this fallback, and two of them are headers that use the macro to add or remove a data member. Any translation unit that includes Application.hpp without the compile definition gets a different sizeof(Application) and different member offsets from the rest of the program — a silent ODR violation that links cleanly and corrupts memory at runtime.

It is latent, not live: all three targets that reach these headers do set the definition today. The problem is that the fallback is precisely what turns “someone forgot the definition on a new target” from a compile error into a memory-corruption bug. That is the wrong default for a flag with ABI consequences.

Delete all eight fallbacks. Replace them with #ifndef SOKOBAN_ENABLE_DEBUG_UI
#error "SOKOBAN_ENABLE_DEBUG_UI must be defined by the build"
#endif, or generate a SokobanConfig.hpp with configure_file and include that instead of relying on a command-line macro at all.

Done. All eight self-defining fallbacks now #error instead, and the flag is defined once — PUBLIC on sokoban_core, which every other target links transitively. That also closes G4: the same generator expression previously appeared three times with mixed PUBLIC/PRIVATE visibility, and two of those were already redundant.

For any real build the change is a no-op — #ifndef X / #error and #ifndef X / #define X 0 are identical when X is defined — so this costs nothing and removes the mechanism that made the failure silent. Reproduced to be sure of what that mechanism was: one header, two translation units, sizeof 4 against 8, linking without a murmur. Checked that every target compiling a guarded file reaches the new definition; the only two test targets that link no Sokoban library, math and geometry, include none of them.

Moderate Constant drift

The point-shadow near plane exists three times, as three unrelated literals

render/LightingConfig.hpp:52 shaders/triangle.frag.glsl:274 shaders/ground_splat.frag.glsl:189

config::pointShadowNearPlane = 0.05f drives the CPU-side projection in VulkanSceneRecorder::projectPointShadow. Moderate Divergent paths

Runtime-appended models skip the descriptor remap the startup path applies

VulkanModelResources.cpp:2506 VulkanModelResources.cpp:236

create() routes every model’s texture dependencies and material bindings through textureCatalog.descriptorIndex() and remapBindingTextures(), because manifest textures live at the low end of the descriptor heap and glTF-discovered maps live at the high end. syncManifestModels() — the Debug decoration-authoring path — pushes definition.textureIndex raw, with no remap at all.

It happens to be correct, because descriptorIndexForLogicalTexture is the identity function below manifestTextureCount_ and editor models only reference manifest textures. But the correctness depends on an invariant stated nowhere, in a function that looks like it simply forgot a step. The same function also builds bindings with base colour only — no normal, metallic-roughness, emissive or occlusion handle — so editor-appended models silently get a lesser material path than manifest-loaded ones.

Call remapBindingTextures unconditionally so both paths read the same, and either extend the binding construction to the full map set or add a comment stating that editor decorations are deliberately base-colour only.

B

The CPU↔GPU contract is maintained by hand

This is the highest-leverage theme in the audit. The handoff is rightly proud that GpuMaterial’s size, alignment and every field offset carry compile-time assertions and were verified against SPIR-V disassembly. That rigour stops at the shader source, where the same structures are retyped by hand and nothing checks them.

Resolved Was: duplication

The shared GPU structs were retyped in every shader that uses them

DeclarationC++ ownerHand-copied into
struct DrawInstanceGpuDrawInstance (256 B)8 shaders
uniform SceneFrameSceneFrameUniform (544 B)6 shaders
struct PointLightDataPointLightUniform (48 B)6 shaders

Adding one vec4 to GpuDrawInstance means editing eight .glsl files correctly and in the same order. Getting it wrong in one of them produces a shader that compiles, validates, and reads the wrong bytes. The static_asserts catch the C++ half of the contract and nothing catches the GLSL half.

The build already uses glslc, which supports #include via GL_GOOGLE_include_directive and -I. There is no technical obstacle here — only that the mechanism was never turned on.

Done. shaders/include/ now holds DrawInstance.glsl, SceneFrame.glsl, Material.glsl, Skinning.glsl, AmbientMask.glsl and PointShadow.glsl; the CMake rule passes -I and each module declares GL_GOOGLE_include_directive. Net 332 deletions against 51 insertions across ten shaders, removing 240 duplicated lines of CPU ↔ GPU ABI.

The acceptance test is the strongest one available for a refactor that claims to change nothing: all sixteen modules compile to byte-identical SPIR-V before and after, and all sixteen pass spirv-val --target-env vulkan1.3. A pilot on the smallest module confirmed up front that the extension directive itself perturbs no codegen. The DEPENDS list now covers every shared header, so editing an ABI rebuilds the modules that read it — without that, the include would have introduced exactly the stale-artifact failure ShaderCatalog.hpp exists to prevent.

A follow-up gpu_abi test closes the other half of the contract. A shared C++/GLSL header was considered and rejected: the layouts already agree exactly, the win after this change is only about fifty lines, and GLSL cannot carry the default member initializers that make GpuMaterial{} the white fallback entry zero depends on. Reading the compiled layout back is strictly stronger — it catches an std140 stride change a shared field list would not — and leaves both declarations readable.

Resolved Was: major · behavioural drift Behavioural drift Corrected

The ground and the scene disagree on how point shadows are filtered

shaders/triangle.frag.glsl:266–310 shaders/ground_splat.frag.glsl:181–210

Correction to the first version of this finding. It claimed these functions were “byte-identical in both files”, inferred from a sliding-window similarity scan. Extracting and diffing them function-by-function while doing B1 showed that only pointShadowWorldDistance is genuinely duplicated. The other two have diverged — which is a worse problem than duplication, and one a mechanical extract would have silently papered over.

pointShadowFactor is the substantive one. The scene shader builds a tangent frame and takes five taps through the shadow cube, averaging them. The ground shader takes one: 

// triangle.frag.glsl — five taps, softened
vec3 offsets[5] = vec3[5](vec3(0.0), tangent, -tangent, bitangent, -bitangent);
for (int sampleIndex = 0; sampleIndex < 5; ++sampleIndex) { /* ... */ }
return 1.0 - shadowed / 5.0 * clamp(light.shadowOptions.w, 0.0, 1.0);

// ground_splat.frag.glsl — one tap, hard edge
float closestDepth = texture(pointShadowMaps, vec4(direction, light.shadowOptions.y)).r;
return 1.0 - shadowed * clamp(light.shadowOptions.w, 0.0, 1.0);

So a point light casts a softened shadow onto a model and a harder, more aliased one onto the ground beside it. shadowFactor differs too, though only cosmetically — the ground rejects out-of-range depth before the UV bounds rather than after, and uses <= 0.0 || >= 1.0 where the scene uses < 0.0 || > 1.0.

Whether the single tap is a deliberate cost saving on a full-screen ground plane or drift that nobody noticed is a question about intent, not about code — which is exactly why it was left alone. Merging it would change how the ground is lit, and that belongs in a change with its own before/after evidence, not inside a refactor that is otherwise provably a no-op.

Unified; the split kept, deliberately. Both bodies moved into shaders/include/PointShadow.glsl — the header B1 created for the one helper they already shared — and each shader now says which shape it wants with a single #define POINT_SHADOW_TAPS. The scene asks for 5, the ground for 1. Nothing about the picture changes; what changes is that the difference is one token in each file instead of something you have to diff two shaders to notice.

Keeping the split is the decision, not an omission. Both shaders loop over up to eight point lights, so five taps on the ground would be up to forty cube-map samples on the largest surface in the frame against eight today. That trade deserves a capture rather than a cleanup, and it is now a one-token experiment when someone wants to run it.

A claim in the earlier version of this finding was also wrong and is withdrawn: I wrote that shadowFactor differed cosmetically between the two. The directional filter is a 3×3 kernel over nine taps in both, identical arithmetic; only the scene's extra depth-range early-out differs. The point-shadow tap count was the only real divergence.

Verified against SPIR-V, which caught a mistake on the way. ground_splat.frag's instruction stream is identical — 797 instructions, zero diff hunks after id canonicalisation — and triangle.frag differs only by a textureSize query being scheduled a few instructions later, same opcode multiset, which is a pure reordering of a side-effect-free query. Both pass spirv-val, and the other fourteen modules are byte-identical.

The mistake: the first attempt shared one loop for both shapes, running it once for the ground on the assumption the compiler would fold a one-iteration loop away. It does not. glslc emitted a real OpLoopMerge with its compare, branch and phi — 204 bytes and 14 instructions of overhead added to the shader whose entire reason for taking one tap is cost. The sampling shape is a compile-time branch now, with that measurement written beside it so the next person does not try the same tidy-looking thing.

Resolved Was: major · fragile encoding Fragile encoding

One vec4 lane carries three unrelated meanings depending on the draw

VulkanSceneRecorder.cpp:1733, 1780, 1881, 1974, 2077, 2257, 2458 shaders/triangle.frag.glsl:202, 217, 79, 645

Seven call sites write GpuDrawInstance::materialOptions, each with a different meaning per lane, and the fragment shader reads several of those meanings without knowing which draw produced it:

LaneWritten asRead as
.x blur flag · face world-origin X · camera X “blur behind” predicate
.y grid size X · UV rect width · belt scroll offset grid-mask gate and material UV scroll
.z grid size Y · UV rect height · manifest texture index grid-mask gate and texture selector
.w ±blur radius (sign = editor preview) · ±water mode · animation time blur radius, dither predicate and highlight pulse clock

.y is the sharpest case: gridMask() treats it as a grid dimension and bails when it is <= 0.0, while materialTextureUv() treats the same lane as a scroll offset added to uv.y. A model draw that ever wanted both would have to choose. textureOptions.y is likewise both a one-based procedural texture handle and an editor-highlight enum, separated only by the draw.gridColor.w < 0.0 flag — a boolean smuggled into an alpha channel as a negative number.

Wider than first reported. Naming the modes showed textureOptions.x is overloaded too, and across pipelines rather than within one: it is a draw mode for the scene, mirror and UI shaders, a base texture handle in ground_splat.frag, and a ripple frequency in water.frag. That is safer than the materialOptions case — a pipeline only ever sees its own draws, so no shader can misread another's lane — but it means the header's field names describe none of the three.

Two options, in increasing order of effort. Cheap: document the union explicitly in VulkanRenderConstants.hpp the way passData already is, naming which draw kind claims which lane. Better: follow the precedent GpuMaterial already set — add a uvec4 of explicit integer lanes carrying a draw-kind tag and the flags, so the shader branches on a named kind instead of inferring it from the sign of an alpha channel.

Traced, documented and pinned; the ABI change deliberately not taken. Adding a draw-kind tag means a new lane in a struct that is exactly full at 256 bytes, and its only proof of correctness is that the picture still looks right — which is not a check this review can run. The cheap option was taken instead, but written from the traced map rather than from the field names.

Tracing it settled the question the finding could not: there is no live defect, and the two things preventing one are unrelated to each other. Most of the apparent overloading is harmless because a pipeline only ever sees its own draws — ground_splat.frag cannot be handed a water instance. The real collision is inside the scene pipeline, where quad draws and model draws share one fragment shader: materialOptions.y is a grid cell width for a face and a scrolling-material UV offset for a model, and gridMask() reads that lane without knowing which produced it. Every model with a scrolling material puts a non-zero value there. What saves it is that gridMask() tests the grid alpha first and a model marks itself with a negative one — a boolean smuggled into an alpha channel turns out to be the only thing standing between an animated model and a grid drawn across it.

Mirror-energy models are the exception that proves how thin this is: they take the other branch and carry no marker, and their grid alpha (0.16) and shadow width (0.38) would both pass gridMask()'s gates. They are safe only because they are routed to a different fragment shader that has no gridMask() — a fact stated nowhere near either the lane or the shader until now.

What landed: the lane union written out per draw kind on GpuDrawInstance, including which of the two mechanisms covers which case; the bare -1.0f named modelDrawMarkerAlpha; the marker's sign test given one spelling as isModelDraw() in DrawMode.glsl; and the second open-coded copy of that test in triangle.frag.glsl replaced by the variable already holding the answer.

Verified by compiling all sixteen shaders before and after: fifteen are byte-identical, including the two others that include DrawMode.glsl, which confirms the new function is stripped when unused. triangle.frag is 16 bytes smaller, and an id-independent instruction diff shows why — one OpLoad and one OpFOrdLessThan gone, being the duplicate comparison, against one added register-level OpCompositeExtract. Both modules pass spirv-val.

The invariant is pinned at both ends rather than described: draw_mode now checks that the marker is negative and that the shader still tests its sign — an equality test would silently reject any other negative a caller is entitled to pick — and scene_draw_lanes checks that a grid colour carrying the marker yields no grid line whatever else is in the lanes. All five mutants of the marker and its shader predicate are caught.

Resolved Was: moderate · correctness Found while extracting D3

Eviction stops after freeing about half of what it needed

render/ResidencyBudget.hpp — needsEviction VulkanModelResources.cpp — makeResident

Choosing a victim raises the pool's retiring total, because that is what retireModel does. The loop that chose it also adds the same bytes to its own scheduledBytes tally. Both then appear in the stop condition, so every victim is subtracted twice: 

resident(1000) - retiring(100) - scheduled(100) + need(250) = 1050 // keep going
resident(1000) - retiring(200) - scheduled(200) + need(250) =  850 // stop
stopped after freeing 200 bytes, although 250 were needed

The publication is then refused, waits for the fence, and retries. So this under-evicts rather than oversubscribing — the hard limit stays honest, and nothing is corrupted. What it costs is latency: an asset takes more publication rounds, and therefore more frames, to become resident under memory pressure than the code reads as intending. It also explains why the ladder ends on a fits check that so often fails.

Fixed. scheduledBytes is gone — from the condition, from the loop, and from the signature. retiring was always the running total the condition wanted: the loop's own victims are in it because retiring one puts them there, and nothing else can be, because the caller refuses to start evicting at all while an earlier retirement is still pending. One tally, not two.

What it was costing, measured. Before changing anything I ran the whole ladder to completion both ways over 200,000 randomised pools, treating one publication attempt plus its fence as a round:

Double-countedFixed
Rounds to publish, mean2.6411.502
Rounds to publish, worst92
Bytes evicted per case4722.44722.4
Evictions per case5.6565.656

The same victims, the same bytes, the same admit-or-block outcome in every one of the 200,000 cases — and in none of them did resident bytes exceed the limit, either way. The fix is not more aggressive eviction, which is what the earlier note assumed and why it was left alone: the total freed was always going to be the shortfall. It just used to arrive in halves, a frame apiece, taking up to nine rounds to do what now takes two. Two is the floor, not a target: one round to choose victims, one to admit after the fence clears, because retiring bytes stay charged until then and that part is deliberate.

ResidencyBudgetTests pinned the old behaviour by name; that test is now evictionFreesTheWholeShortfallInOneRound, and it checks the retry too. Five mutants of the corrected condition are all caught, including one that restores the original double count exactly.

One thing to confirm on a real build. Run the 64 KiB stress capture the handoff records: --smoke-frames 240 --require-validation --texture-residency-kib 64 --evidence-output build\a3-mip-evidence. Resident bytes must stay bounded at 65,536 and validation must stay clean — those falsify the fix if they move. Retained mip levels (37/46 archived) and the set of reduced textures may legitimately differ: publications now land in different frames, and TextureMipResidency chooses a mip tail from the capacity available at publication time. A different split is worth a look, not an alarm.

The counters that answer this were not in the capture at all. Residency evictions and capacity blocks were reachable only from the debug panel, which a headless smoke run never draws — so the two numbers that say whether residency was under pressure and whether it coped were missing from exactly the runs taken to find out. The smoke summary now logs them beside the mip line it already wrote.

Result of the capture, and a correction. On a current binary the run reports 63376 / 65536 bytes, 37 / 46 mip levels, five reduced textures and 831232 bytes omitted — character for character the archived baseline. Bounded, validation-error free, and the mip split did not move. That is the half of the prediction that mattered for safety, and it holds.

The other half is still unmeasured, because I named the wrong number to watch. I said capacity blocks should fall. The run shows 3,324 of them against only 11 evictions in 240 frames — so the eviction loop barely ran, and almost every refusal never reached it. One counter was being incremented for three unrelated reasons: an asset larger than the whole budget, a compressed texture with no mip tail that fits, and eviction finding nothing it was allowed to take. Under a deliberately tiny 64 KiB budget the first two are permanent and expected — roughly 13.9 refusals per frame is the same handful of oversized textures being retried every frame — and they swamp the third, which is the only one this fix touches. A single number adding those together cannot answer the question it was added to answer.

The counter is now three: residencyOversizedBlocks, residencyMipPlanBlocks and residencyNoVictimBlocks, with the total kept. The smoke summary and the debug panel both report the split. Only the third is pressure; the first two are the budget being smaller than the content, which is what a stress run is for.

Note also that model residency sat at 1,775,756 of 134,217,728 bytes — the model pool was never under pressure at all, so this capture exercises the eviction path only for textures. A run that actually stresses both would need a model budget override, which does not currently exist.

C

Size, structure and readability

The codebase is well modularised at the file level — 279 files with clear ownership boundaries. The pressure is inside a handful of specific functions and one class.

Major God object

VulkanModelResources owns eight things at once

VulkanModelResources.cpp — 2,710 lines VulkanModelResources.hpp — 557 lines

3,267 lines, 40 private members and 60-odd methods covering: mesh loading and upload; texture loading, format selection, mip generation and upload; animation clip loading; the skinning palette buffer; the draw-instance buffer; the material buffer and its free-list allocator; two residency budgets with eviction and fence-owned retirement; and the descriptor-heap index mapping. Any one of those is a reasonable class.

The consequences are visible in the file: the load-state machine (Unrequested → Queued → Loading → CpuReady → Uploading → Ready) is implemented three times, once per asset kind, with each copy slightly different — publishModel recurses into itself, publishTexture falls through, publishAnimation has no CPU-ready phase at all. A reader has to hold all three in their head to be confident about any one.

The natural seams are already visible in the member list. Split out ModelGeometryStore (models, meshes, bounds, materials), TextureHeap (slots, definitions, uploads, descriptor mapping) and ResidencyBudget (budgets, victim selection, retirement) — the last is the easiest first cut because makeModelResident and makeTextureResident are already the same algorithm twice. Then template the shared load-state machine over the slot type so the three copies collapse into one.

Two seams cut, the class split still open. Residency and retirement moved out first (ResidencyBudget.hpp, 66 checks). The material buffer's allocator has now followed it into MaterialRangeAllocator.hpp: the bump pointer, the first-fit reuse and the coalescing free list, with the capacity passed in rather than stored, and no Vulkan in sight. writeMaterials is down to allocating a base and writing the bytes; releaseMaterialRange no longer exists as a method, because it was the free list and the free list now owns itself. Together the two extractions take about 180 lines out of the class.

Both of these were policy that could not be reached from a test — private methods behind a live device. The allocator now has 49 checks, including the two behaviours that were surprising enough to pin rather than quietly change: releasing the same run twice is absorbed silently, and fragmentation can refuse a run the buffer has total room for, which is the real failure mode behind “Material buffer is exhausted” appearing while the buffer looks half empty.

Both descriptions of all four blocks are machine-checked against each other on every build.
